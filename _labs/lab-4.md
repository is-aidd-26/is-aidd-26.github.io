# Лабораторная 4: Автоматизация качества и TDD

Для публикации в систему ASAP используйте ветку `04_quality_gates`

## Цели

**Основная цель:** внедрить в проект проверки с помощью инструментов, основанных на алгоритмах и формальных языках, чтобы компенсировать стохастическую природу LLM и связанные с ней проблемы.

**Дополнительная цель:** достичь не менее 70% покрытия кода тестами для бэкенда (метрика line coverage)

## Задания

Обязательные задания:

1. Подключить подходящие для вашего языка линтеры со строгими проверками
2. Подключить автоформатирование кода
3. Написать модульные и интеграционные тесты бэкенда

Необязательные задания (выполняются по желанию студента):

1. Настроить автоматическую проверку на уровень line coverage — не менее 70%
2. Встроить в `AGENTS.md` требования по покрытию сценариев использования тестам
    - пример: «каждое требование должно иметь как минимум один тест на успешный сценарий»
3. Вести разработку в ИИ-агенте по правилам Canon TDD
    - сначала ИИ-агент согласует с вами список тестов
    - затем ИИ-агент пишет тесты без реализации и проверяет, что они падают
    - затем ИИ-агент пишет реализацию, не меняя тесты (за исключением исправления явных ошибок в тестах)
4. Написать модульные, снапшотные либо интеграционные тесты фронтенда
5. Написать сквозные (end-to-end) тесты, проверяющие фронтенд и бэкенд вместе

## Требования

### Общие требования

Эти требования применяются для любого технологического стэка:

1. Сборка, линтеры и тесты выполняются без ошибок и предупреждений
2. Показатель line coverage (покрытие строк кода тестами) для бэкенда не менее 70%
3. Есть модульные тесты бэкенда
4. Есть интеграционные тесты бэкенда

По желанию можно добавить сквозные тесты — если вы их добавляете, то следует использовать playwright, puppeteer либо selenium.

### Требования к модульным тестам

1. По возможности следует использовать параметризованные тесты
2. Не должно быть тривиальных тестов — проверка небольших методов, конструкторов и т.д. вместо проверки соответствия модуля ожиданиями

### Требования к интеграционным тестам

1. Написаны на том же языке, что и тестируемый ими бэкенд, и запускают приложение в памяти
    - для C# — можно использовать TestServer
    - для Go — можно использовать пакет httptest
2. Запускаются с настоящей СУБД — с помощью библиотеки testcontainers или иного механизма
3. Проверяют методы API и другие публичные контракты системы вместо вызова внутренних API (т.е. методов классов системы)
4. Проверяют реальные бизнес-требования с акцентом на успешные сценарии
5. Минималистичны и полны: минимальное число сценариев обеспечивает максимальное покрытие бизнес-требований
6. Не должно быть тривиальных тестов — проверок несущественных особенностей поведения или неправдоподобных corner cases
7. Не должно быть интеграционных тестов для того, что легко проверяется модульным тестами

### Измерения покрытия кода тестами

1. В проекте должен быть скрипт, который прогоняет тесты и генерирует HTML-отчёт о покрытии кода тестами
    - скрипт может быть написан на bash, python 3 или PowerShell
    - для проектов на Go допускается вместо скрипта сделать цель в Makefile
2. В README в инструкции по сборке должен быть описан способ запуска скрипта генерации HTML-отчёта о покрытии кода тестами
3. Из измерения покрытия кода тестами нужно исключать генерируемый код (если он есть)

## Особые требования для Go

1. Используется Go 1.27 или выше
2. Настроен линтер golangci-lint, при этом включены линтеры
    - modernize — повышает идиоматичность кода
    - gocritic — повышает идиоматичность кода
    - revive:exported — экспорт обязан иметь godoc о предназначении;
    - errorlint — проверяет обработку ошибок
    - contextcheck — проверяет передачу `context.Context`
    - wastedassign — находит бесполезные присваивания
    - gosec — проверяет проблемы безопасности
    - depguard — фиксирует зависимости
    - misspell — улучшает читаемость
    - unconvert — улучшает читаемость
    - nakedret — улучшает читаемость
3. Тесты для проверок (asserts) используют функции из пакета "github.com/stretchr/testify/require"
4. Интеграционные тесты должны использовать библиоетку TestContainers для запуска СУБД

## Особые требования для C#

Для сборки должен использоваться .NET 10 или выше.

В файле `Directory.Build.props` в корне проекта должны быть следующие опции:

1. Режим «предупреждения трактуются как ошибки» — `<WarningsAsErrors>true</WarningsAsErrors>`
2. Подключены линтеры `Microsoft.CodeAnalysis.NetAnalyzers`, `Roslynator.Analyzers`, `StyleCop.Analyzers`, `xunit.analyzers`

Интеграционные тесты:

1. Должны использовать XUnit для запуска
2. Должны использовать библиотеку TestContainers для запуска СУБД

Для измерения покрытия кода тестами следует использовать библиотеку Coverlet: [Анализ покрытия тестами кода для C#/.NET](https://compilers-course.ru/docs/articles/dotnet-code-coverage/).

## Особые требования для Python

1. В качестве линтера и автоформатировщика следует использовать `ruff`
2. В качестве менеджера пакетов следует использовать `uv`
3. Нужно подключить к проекту [wemake-python-styleguide](https://github.com/wemake-services/wemake-python-styleguide)

## Контроль минимального порога покрытия тестами

>Это необязательное задание.

Для C# контролировать уровень покрытия кода тестами можно путём настройки Coverlet:

- Threshold: 70
- ThresholdType: line
- ThresholdStat: Minimum

Например, можно запускать тесты с проверкой порога покрытия:

```bash
dotnet test /p:CollectCoverage=true /p:Threshold="70" /p:ThresholdType="line"
```

## Разработка по Canon TDD с агентом

>Это необязательное задание.

Можно сформулировать в AGENTS.md правило в таком духе:

```markdown
All reusable library code is developed strictly by Canon TDD:

1. Write a **Test List** — minimal unit tests plan, focused on happy paths;
2. Pause for human review of the list;
3. Write the tests. They must fail to run or even fail to compile;
4. Pause for human review of the tests;
5. Write the implementation. On any test failure, analyze the root cause
   and fix the real problem — never bend code and tests to match each other. When problem is ambiguous, report a problem to human and ask for solution.
```

Учитывайте, что в 2026 году любая LLM плохо составляет список тестов и плохо видит возможности рефакторинга кода — это ответственность разработчика.
