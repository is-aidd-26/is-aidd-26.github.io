# Лабораторная 5: Контейнеризация и стресс-тесты

Для публикации в систему ASAP используйте ветку `05_stress_tests`

## Цели

Основные цели:

1. Завершить контейнеризацию компонентов
2. Обеспечить способность сервиса держать нагрузку в условиях ограниченных ресурсов

## Задания

Обязательные задания

1. Настроить маршрутизацию входящего трафика, чтобы фронтенд и бэкенд отдавались с одного порта на localhost
2. Настроить запуск в docker compose всех контейнеров, включая бэкенд и фронтенд
3. Перейти на клиент-серверную СУБД, если на предыдущих этапах использовался SQLite
4. Устранить узкие места в получении сообщений и чатов
5. Подготовить скрипты для симуляции нагрузки на сервис
6. Провести стресс-тестирование в условиях намеренно ограниченных ресурсов

## Маршрутизация входящего трафика

Есть два способа реализации работы фронтенда и бэкенда на одном адресе:

1. Добавить nginx в роли обратного прокси, маршрутизирующего запросы между бэкендом и фронтендом
2. Реализовать маршрутизацию запросов к фронтенду через бэкенд

### Добавление nginx в роли обратного прокси

В этой схеме:

1. В docker compose появляется контейнер nginx, который слушает порт, отображаемый на порт хоста
2. Контейнер с nginx маршрутизирует входящий трафик между контейнерами бэкенда и фронтенда
    - можно запросы с префиксом `/api/` в URL Path направлять на бэкенд, а остальные — на фронтенд
    - можно изолировать фронтенд по префиксу `/app` в URL Path, а остальные запросы направлять на бэкенд
    - можно использовать иные префиксы, если в целом схема остаётся корректной

Подробности см. в статье [Маршрутизация трафика через nginx](/guides/nginx-ingress).

### Маршрутизация запросов к фронтенду через бэкенд

В этой схеме:

1. В docker compose контейнер бэкенда слушает порт, отображаемый на порт хоста
2. Бэкенд обрабатывает запросы к API и дополнительно проксирует запросы к статическим файлам фронтенда
    - можно запросы с префиксом `/api/` в URL Path направлять на бэкенд, а остальные — на фронтенд
    - можно изолировать фронтенд по префиксу `/app` в URL Path, а остальные запросы направлять на бэкенд
    - можно использовать иные префиксы, если в целом схема остаётся корректной

Если вы пишете на C# и ASP.NET Core, то вы можете:

1. Для проксирования на фронтенд с учётом потребностей dev-версии использовать методы расширения из NuGet-пакета [Microsoft.AspNetCore.SpaServices.Extensions](https://www.nuget.org/packages/Microsoft.AspNetCore.SpaServices.Extensions)
    - `SpaApplicationBuilderExtensions.UseSpa`;
    - `SpaProxyingExtensions.UseProxyToSpaDevelopmentServer`.
2. Для разделения обработки запросов по префиксу использовать метод расширения `WebApplication.MapWhen`.

### Base URL для фронтенда

Если вы используете фреймворк React и vite для сборки, вы можете определить базовый URL для фронтенда с помощью опции "base", чтобы изолировать фронтенд по префиксу `/app`:

```js
// vite.config.js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  base: '/app/', // Все ассеты будут запрашиваться по пути /app/...
})
```

## Запуск всех контейнеров в docker-compose

Нужно запускать все контейнеры в docker-compose — включая фронтенд, бэкенд, СУБД и остальные компоненты, такие как nginx. Набор контейнеров зависит от особенностей вашего проекта.

Можно организовать сборку образов бэкенда и фронтенда при запуске docker-compose, используя опцию `build:` и несколько Dockerfile, при этом:

1. Для сборки через Dockerfile рекомендуется использовать multi-stage build
    - образ с SDK и инструментами использовать для стадии сборки проекта;
    - образ с runtime зависимостями использовать как среду выполнения.
2. Рекомендуется правильно настроить кэширование зависимостей при сборке docker-образа
    - обычно для этого файлы с описанием зависимостей, такие как `package.json` и `package-lock.json`, копируются в собираемый образ прежде остальных файлов проекта, затем запускаются команды установки зависимостей, затем копируется исходный код, и лишь затем выполняются команды сборки без установки зависимостей
    - этот способ позволяет избежать пересборки слоя, скачивающего зависимости из Интернета, при изменении каких-либо файлов проекта

### Искусственное ограничение ресурсов

Вы должны ограничить потребление ресурсов контейнерами при запуске в docker-compose до минимума и даже ниже минимума.

- Конкретные параметры вы выбираете сами;
- Созданная конфигурация compose должна позволять развернуть все контейнеры на виртуальной машине с 1 ядром CPU и 1 ГБ памяти, где часть памяти резервируется под нужды ОС, а остальное все контейнеры используют совместно.

Для этого можно использовать секцию deploy в параметрах сервисов в docker-compose, например:

```yaml
services:
  backend:
    # ...
    # Ограничиваем ресурсы контейнера.
    deploy:
      resources:
        # Потолок использования ресурсов контейнером.
        limits:
          # Контейнер использует не более 50% времени одного ядра CPU.
          # При попытке использовать больше будет CPU throttling.
          cpus: "0.5"
          # Контейнер использует не более 256 мегабайт памяти.
          # При попытке использовать больше случится OOM и процесс будет убит ядром Linux.
          memory: 256M
        # Базовый минимум ресурсов, проверяемый при запуске (необязательно).
        reservations:
          cpus: "0.25"
          memory: 128M
    # Ограничиваем размер логов контейнера.
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

Стресс-тестирование скриптом в рамках этой лабораторной нужно проводить на жёстко ограниченных вами ресурсах docker-контейнеров.

### Ограничения для Postgres

Для Postgres нужно:

1. Ограничить потребление CPU и memory контейнером
2. Через переменные окружения или файл конфигурации снизить лимит одновременных соединений на сервере Postgres, чтобы он не вышел за лимиты памяти при большом количестве одновременных запросов со стороны бэкенда;
3. Со стороны бэкенда правильно настроить использование общего пула соединений (_англ._ connection pool).

### Настройки healthcheck

Для всех docker-контейнеров в конфиге docker-compose должны быть проставлены корректные healthcheck, что позволит в любой момент оценивать состояние всех запущенных контейнеров.

Пример:

```yaml
services:
  backend:
    # ...
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:8081/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 5s
```

## Клиент-серверная СУБД

На этой итерации вы должны окончательно перейти на использование клиент-серверной реляционной СУБД, если вы не сделали этого раньше.

1. Рекомендуется Postgres, допускаются MySQL и другие клиент-серверные реляционные СУБД
2. SQLite не допускается даже в клиент-серверном варианте, поскольку он спроектирован как встраиваемая в приложение СУБД
3. Интеграционные тесты бэкенда должны использовать библиотеку testcontainers для запуска docker-контейнера с СУБД
4. Вне интеграционных тестов СУБД должна запускаться через docker-compose

Наличие реляционной СУБД не означает запрета на иные сервисы и хранилища. Вы можете использовать иные компоненты, если они вам нужны, например:

- centrifugo для отправки новых сообщений от сервера к клиенту через веб-сокеты или иной подходящий транспорт;
- redis для кэширования;
- или иной компонент, использование которого выглядит оправданным.

## Устранить узкие места в получении сообщений и чатов

Для мессенджера и чата техподдержки самая нагруженная функция — это получение чатов и сообщений.

Простейший способ получения новых чатов и сообщений — периодический опрос (_англ._ polling) за счёт отправки HTTP-запросов от клиента к серверу. Однако это создаёт дилемму:

1. Если каждый клиент постоянно опрашивает сервер, то в масштабе будет огромная нагрузка на сервер и на сеть, что неприемлемо для поставщика сервиса
2. Если клиент реже опрашивает сервер, то новые сообщения и чаты доставляются с задержкой, что неприемлемо для пользователя

Решение — оптимизация способа получения клиентом как начального состояния, так и обновлений:

1. Оптимизировать на бэкенде обработку операций чтения, а именно: получение списка чатов, получение сообщений чата и другие операции, выполняемые постоянно
2. Доставлять обновления по двустороннему каналу, сообщения в который могут отправляться по инициативе сервера, а не только клиента

### Требования

1. Информация о новых чатах и сообщениях должна доставляться через транспорт, поддерживающий отправку сообщений сервером
    - в роли транспорта рекомендуется websocket, допускается иной вариант: Server-Sent Events, HTTP-Streaming;
    - для C#/.NET рекомендуется использовать SignalR, а не работать с websocket или иным протоколом напрямую;
    - для Go / Python можно либо добавить новый компонент Centrifugo, либо работать с websocket или иным протоколом.
2. Операции чтения, вызываемые при обычной навигации по фронтенду, должны быть оптимизированы для экономии ресурсов сервера и быстрой работы
    - не должно быть N+1 Query Problem при работе с СУБД или работе с API бэкенда;
    - не должно быть дорогих операций после извлечения данных из СУБД — например, не следует реализовывать соединения таблиц или пагинацию путём операций над списками и словарями на бэкенде;
    - если уместна пагинация, то она должна быть добавлена и должна работать оптимально — например, за счёт курсорной пагинации;
3. В тех же операциях чтения не должно быть получения излишних данных
    - при открытии главной страницы мессенджера не следует загружать повторно все сообщения всех чатов;
    - при открытии чата не следует загружать всю историю сообщений.
4. Допустимо, но не рекомендуется добавлять кэширующий компонент — например, Redis
    - в рамках текущей нагрузки в этом нет реальной необходимости, реляционной СУБД достаточно;
    - реализация внешнего кэша может создать новые риски производительности и надёжности системы.
5. Оптимизация не должна существенно ограничивать функциональность
    - например, в мессенджере в списке чатов обычно отображается последнее сообщение в каждом чате — этим не следует жертвовать ради оптимизации.

## Скрипт симуляции нагрузки на сервис

Цель скрипта — проверить способность держать нагрузку у бэкенда и сопуствующих компонентов, таких как Postgres и nginx.

Требования к скрипту:

1. Этот скрипт можно разработать на Python 3 или ином удобном языке программирования.
2. Скрипт должен симулировать общение N пользователей с использованием базовый функций вашего сервиса.
3. Скрипт должен иметь простые в использовании опции для регулирования нагрузки — например, для установки числа пользователей или скорости их общения.
4. Скрипт должен быть избавлен от внутренних проблем, мешающих создать нормальную нагрузку со стороны клиента, а именно:
    - если скрипт на Python 3, то не следует всю работу совершать из одного потока — лучше использовать пул потоков;
    - не рекомендуется использовать блокирующие поток операции — вместо них лучше использовать async/await или иной механизм, подходящий для вашего скриптового языка.
5. Скрипт должен проверять статусы ответов и писать сводную статистику по ним.
6. Скрипт может запускать, а может и не запускать фоновый браузер — то есть допускается как запрашивать API бэкенда в обход фронтенда, так и работать с бэкендом через фоновый браузер.

Как может работать симуляция действий пользователя внутри скрипта:

1. N пользователей периодически пишут что-либо друг другу в личных и групповых чатах
2. Они могут использовать шаблонные фразы и ответы на них, например:
    - Привет!
    - Как дела?
    - Какой твой любимый цвет?
    - Какое твоё любимое животное?
    - Почему небо голубое?
    - Почему луна у горизонта выглядит крупнее?
3. Число пользователей и темп их общения задаётся аргументами и опциями скрипта

Не рекомендуется делать чрезмерно сложную симуляцию, а также встраивать в неё ML-модели или LLM.

## Стресс-тестирование

Вы должны провести стресс-тестирование своей системы с помощью своего скрипта и определить, какое число пользователей и с какой интенсивностью общения может выдерживать ваш сервис, в том числе при длительной работе скрипта — порядка 10 минут.

Если стресс-тестирование показало явные узкие места — исправьте их.
