# Лабораторная 5: Контейнеризация и стресс-тесты

Для публикации в систему ASAP используйте ветку `05_stress_tests`

## Цели

Основные цели:

1. Добавить контейнеризацию ресурсов
2. Подготовить инструменты стресс-тестирования
3. Проверить способность сервиса держать нагрузку в условиях ограниченных ресурсов

## Задания

Обязательные задания

1. Настроить маршрутизацию входящего трафика, чтобы фронтенд и бэкенд отдавались с одного порта на localhost
2. Настроить запуск в docker compose всех контейнеров, включая бэкенд и фронтенд
3. Перейти на клиент-серверную СУБД (рекомендуется Postgres), если на предыдущих этапах использовался SQLite
4. Подготовить скрипты для симуляции нагрузки на сервис
5. Провести стресс-тестирование в условиях искусственно ограниченных ресурсов

## Маршрутизация входящего трафика

Есть два способа реализации ingress — то есть маршрутизатора входящего трафика:

1. Добавить nginx в роли обратного прокси, маршрутизирующего запросы между бэкендом и фронтендом
2. Реализовать маршрутизацию запросов к фронтенду через бэкенд

### Добавление nginx в роли обратного прокси

В этой схеме:

1. В docker compose появляется контейнер nginx, который слушает на порт с хоста
2. Nginx принимает весь входящий трафик и маршрутизирует его между контейнерами бэкенда и фронтенда
    - можно запросы с префиксом `/api/` в URL Path направлять на бэкенд, а остальные — на фронтенд
    - можно наоборот изолировать фронтенд по префиксу `/app` в URL Path, а остальные запросы направлять на бэкенд

Подробности см. в статье [Маршрутизация трафика через nginx](/guides/nginx-ingress).

### Маршрутизация запросов к фронтенду через бэкенд

В этой схеме:

1. В docker compose бэкенд слушает на порт с хоста
2. Бэкенд проксирует запросы к фронтенду
    - можно запросы с префиксом `/api/` в URL Path направлять на бэкенд, а остальные — на фронтенд
    - можно наоборот изолировать фронтенд по префиксу `/app` в URL Path, а остальные запросы направлять на бэкенд

Если вы пишете на C# и ASP.NET Core, то вы можете использовать для этой цели метод расширения `UseProxyToSpaDevelopmentServer` из NuGet-пакета [Microsoft.AspNetCore.SpaServices.Extensions](https://www.nuget.org/packages/Microsoft.AspNetCore.SpaServices.Extensions)

### Base URL для фронтенда

Если вы используете фреймворк React и vite для сборки, вы можете определить базовый URL для фронтенда с помощью опции "base", чтобы изолировать фронтенд по префиксу `/app`:

```js
// vite.config.js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  base: '/app/', // Все ассеты будут запрашиваться по пути /app/...
})
```

## Запуск всех контейнеров в docker-compose

Нужно запускать все контейнеры в docker-compose — включая фронтенд, бэкенд, СУБД и остальные компоненты, такие как nginx. Набор контейнеров зависит от компонентов в вашем проекте.

1. Можно организовать сборку образов бэкенда и фронтенда при запуске docker-compose, используя опцию `build:` и несколько Dockerfile
2. Рекомендуется использовать multi-stage build для сборки через Dockerfile
3. Рекомендуется правильно настроить кэширование зависимостей при сборке docker-образа
    - обычно для этого файлы с описанием зависимостей, такие как `package.json` и `package-lock.json`, копируются в собираемый образ прежде остальных файлов проекта
    - это позволяет избежать пересборки слоя, скачивающего зависимости из Интернета, при изменении каких-либо файлов проекта

### Искусственное ограничение ресурсов

Вы должны ограничить потребление ресурсов контейнерами при запуске в docker-compose до минимума и даже ниже минимума.

- Конкретные параметры вы выбираете сами;
- Конечная цель — конфигурация compose должна позволять развернуть все контейнеры на виртуальной машине с 1 ядром CPU и 1 ГБ памяти, где часть этой памяти резервируется под нужды ОС, а остальное все контейнеры используют совместно.

Для этого можно использовать секцию deploy в параметрах сервисов в docker-compose, например:

```yaml
services:
  backend:
    # ...
    # Ограничиваем ресурсы контейнера.
    deploy:
      resources:
        # Потолок использования ресурсов контейнером.
        limits:
          # Контейнер использует не более 50% времени одного ядра CPU.
          # При попытке использовать больше будет CPU throttling.
          cpus: "0.5"
          # Контейнер использует не более 256 мегабайт памяти.
          # При попытке использовать больше случится OOM и процесс будет убит ядром Linux.
          memory: 256M
        # Гарантированный минимум, проверяемый при запуске (необязательно).
        reservations:
          cpus: '0.25'
          memory: 128M
    # Ограничиваем размер логов контейнера.
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

Стресс-тестирование скриптом в рамках этой же лабораторной нужно проводить на жёстко ограниченных вами ресурсах docker-контейнеров.

Для Postgres нужно:

1. Ограничить потребление CPU и memory контейнером
2. Через переменные окружения или файл конфигурации снизить лимит одновременных соединений на сервере Postgres, чтобы он не вышел за лимиты памяти при большом количестве одновременных запросов со стороны бэкенда;
3. Со стороны бэкенда правильно настроить использование общего пула соединений (_англ._ connection pool).

### Настройки healthcheck

Для всех docker-контейнеров в конфиге docker-compose должны быть проставлены корректные healthcheck, что позволит в любой момент оценивать состояние всех запущенных контейнеров.

Пример:

```yaml
services:
  backend:
    # ...
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:8081/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 5s
```

## Клиент-серверная СУБД

На этой итерации вы должны окончательно перейти на использование клиент-серверной реляционной СУБД:

1. Рекомендуется Postgres, допускаются MySQL и другие клиент-серверные реляционные СУБД
  - SQLite не допускается, даже в клиент-серверном режиме
2. Интеграционные тесты бэкенда должны использовать библиотеку testcontainers для запуска docker-контейнера с СУБД
3. Вне интеграционных тестов СУБД должна запускаться через docker-compose

Допускаются дополнительные компоненты, если они вам нужны, например:

- centrifugo для отправки новых сообщений от сервера к клиенту через веб-сокеты или иной подходящий транспорт;
- redis для кэширования;
- или иной компонент, использование которого выглядит оправданным.

## Скрипт симуляции нагрузки на сервис

Цель скрипта — проверить способность бэкенда и сопуствующих компонентов, таких как Postgres и nginx, держать нагрузку на сервис.

Требования к скрипту:

1. Этот скрипт можно разработать на Python 3 или ином удобном языке программирования.
2. Скрипт должен симулировать общение N пользователей
3. Скрипт должен иметь простые в использовании опции для регулирования нагрузки — например, для установки числа пользователей или интенсивности их общения
4. Скрипт должен быть избавлен от внутренних проблем, мешающих создать нормальную нагрузку, а именно:
    - если скрипт на Python 3, то не следует все запросы отправлять из одного потока — лучше использовать пул потоков или иное решение
    - не рекомендуется использовать блокирующие поток операции — вместо них лучше использовать async/await или иной механизм, подходящий для вашего скриптового языка
5. Скрипт должен фиксировать статусы ответов
6. Скрипт может запускать, а может и не запускать фоновый браузер — допускается запрашивать API бэкенда в обход фронтенда.

Как может работать скрипт для мессенджера:

1. N пользователей периодически пишут что-либо друг другу в личных и групповых чатах
2. Они могут использовать шаблонные фразы и ответы, например:
    - Привет!
    - Как дела?
    - Какой твой любимый цвет?
    - Какое твоё любимое животное?
    - Почему небо голубое?
    - Почему луна у горизонта выглядит крупнее?

Не рекомендуется делать чрезмерно сложную симуляцию, а также встраивать в неё ML-модели или LLM.

## Стресс-тестирование

Вы должны провести стресс-тестирование своей системы с помощью своего скрипта и определить, какое число пользователей и с какой интенсивностью общения может выдерживать ваш сервис, в том числе при длительной работе скрипта — порядка 10 минут.
