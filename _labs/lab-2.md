## Цели

**Основная цель:** на основе PRD и OpenAPI из лабораторной №1 спроектировать архитектуру и модель данных мессенджера / чата техподдержки, обосновать ключевые решения и подготовить документацию, достаточную для реализации проекта.

**Дополнительная цель:** применить облачные AI-инструменты для проектирования архитектуры и базы данных, сравнить их применимость, зафиксировать проверенные результаты и ограничения. 

---

## Задания

### Обязательные
1. **Взять за основу результаты лабораторной №1**
    - выбранный вариант проекта;
    - PRD;
    - OpenAPI v3;
    - выбранные дополнительные фичи;
2. **Сформулировать нефункциональные требования**
    - производительность: задержка доставки, число одновременных пользователей;
    - надёжность: доступность, восстановление после сбоев;
    - безопасность: аутентификация, авторизация, защита данных;
    - приватность: если проект про анонимность или безопасность;
    - масштабируемость: что должен выдержать MVP;
    - наблюдаемость: логи, метрики, трассировка;
    - ограничения: сроки, стек, стоимость инфраструктуры.
3. **Выбрать архитектурный стиль и обосновать**
    - например, модульный монолит для MVP;
    - при необходимости — отдельный realtime-шлюз для WebSocket/SSE;
    - явно объяснить, почему не выбраны микросервисы, если они не нужны;
    - решение должно быть реалистичным для студента за 3 месяца.
4. **Спроектировать C4-диаграммы**
    - Context — система и внешние акторы;
    - Container — frontend, backend, БД, realtime-компонент, кэш;
    - Component — минимум для одного ключевого сервиса (например, message service).
5. **Описать ключевые сценарии**
    - sequence diagram для отправки сообщения;
    - sequence diagram для получения сообщения;
    - сценарий для выбранной дополнительной фичи: реакции, отложенные сообщения, статус, автоудаление и т.п.
6. **Спроектировать модель данных**
    - ERD;
    - таблицы, поля, типы, первичные и внешние ключи;
    - связи и ограничения;
    - индексы под основные запросы;
    - обоснование нормализации / денормализации;
    - учесть выбранные фичи: групповые чаты, избранное, emoji, статусы, реакции, отложенные сообщения, автоудаление.
7. **Уточнить контракты API и событий**
    - проверить, не противоречит ли OpenAPI из ЛР1 архитектуре;
    - описать WebSocket/SSE-события, если они нужны;
    - зафиксировать формат ошибок;
    - при изменениях обновить `openapi.yaml`.
8. **Подготовить ADR**
    - 3–5 Architecture Decision Records;
    - например: выбор монолита, выбор PostgreSQL, выбор WebSocket, стратегия хранения сообщений, способ аутентификации.
9. **Оформить отчёт об использовании AI-инструментов**
    - какие облачные инструменты использовались;
    - какие промпты применялись;
    - что сгенерировано, что проверено вручную;
    - какие проблемы встретились, как решили.
10. **Оформить документацию в репозитории**
    - `docs/architecture.md`
    - `docs/database.md`
    - `docs/adr/ADR-*.md`
    - `docs/diagrams/*.mmd`
    - `docs/ai-tools-report.md`
    - при необходимости обновлённый `openapi.yaml`
### Необязательные
- создать скелет репозитория: `frontend/`, `backend/`, `docs/`, `docker-compose.yml`, `.env.example`;
- сгенерировать DDL или миграции для выбранной БД;
- поднять PostgreSQL и заглушку backend в Docker Compose;
- реализовать один метод API, который пишет сообщение в лог;

## Требования

### Требования к архитектурной документации
- Документ написан студентом или полностью вычитан студентом.
- Описаны все функциональные и нефункциональные требования.
- Документ легко читается человеком.
- Проверен LLM по аспектам:
    - полнота: нет «слепых пятен»;
    - нет противоречий внутри документа;
    - нет логических, фактических, грамматических и стилевых ошибок;
    - нет ошибок форматирования Markdown;
    - достижимость: проект можно реализовать за три месяца параллельно с другими курсами.
- Есть трассируемость: фича из PRD → компонент → API/событие → таблица БД.
- Архитектура не противоречит OpenAPI из ЛР1.

### Требования к диаграммам

- Диаграммы хранятся в репозитории в текстовом формате: Mermaid (в markdown файлах).
- Диаграммы рендерятся без ошибок.
- C4 Context и Container обязательны.
- Минимум одна Component-диаграмма.
- Минимум две sequence diagram.
- ERD обязательна.
- Названия сущностей и компонентов согласованы с текстом и OpenAPI.

### Требования к модели данных
- Есть ERD.
- Для таблиц указаны поля, типы, ключи, ограничения.
- Есть индексы под основные запросы.
- Обоснована нормализация или денормализация.
- Учтены выбранные дополнительные фичи.
- Нет противоречий между моделью данных и сценариями использования.
- Если есть DDL/миграции, они применяются без ошибок.

### Требования к использованию AI-инструментов

- Использован минимум один облачный AI-инструмент.
- Зафиксированы промпты и результаты.
- Проведена ручная проверка сгенерированных решений.
- Описаны ограничения, галлюцинации и способы их обнаружения.

### Требования к репозиторию и сборке (если делается необязательная часть)

- В `README.md` описано, как собрать и запустить проект.
- Инструкция работает на Unix-системе: OSX / Linux.
- Сборка выполняется без ошибок и предупреждений.
- Если backend отсутствует, есть работоспособная заглушка.
- Если есть тесты, они выполняются без ошибок и предупреждений.
