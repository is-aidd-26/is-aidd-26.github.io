# Лабораторная 2: Проектируем архитектуру

## Цели

**Основная цель:** спроектировать архитектуру системы и схему базы данных, опираясь на PRD и OpenAPI-схему из предыдущей лабораторной.

**Дополнительные цели:** реализовать хранение данных в СУБД, подготовить ADR

## Задания

Обязательные:

1. Спроектировать архитектурные диаграммы по модели C4
2. Спроектировать логическую и физическую схемы базы данных

Необязательные:

1. Добавить в бэкенде слой доступа к данным и хранение данных в СУБД
2. Сформулировать ключевые архитектурные решения и записать их в ADR

## Требования

### Требования к архитектурным диаграммам

1. Все артефакты должны быть в каталоге `docs/` — например, в `docs/diagrams/` или `docs/c4/`
2. Диаграммы реализуются с помощью языка разметки — Mermaid либо PlantUML
3. Архитектурные диаграммы строятся по модели С4, нужны артефакты на каждый из 4 уровней C4:
    - Одна диаграмма C4 Context — система и внешние акторы;
    - Одна диаграмма C4 Container — фронтенд, бэкенд, СУБД (допускаются и другие единицы развёртывания)
    - Одна диаграмма C4 Component — для бэкенда либо для фронтенда
    - (По желанию) одна диаграмма классов для уровня C4 Code
    - Две диаграммы последовательностей: отправка сообщения, получение сообщения
    - (По желанию) третья диаграмма последовательностей для дополнительной фичи из вашего PRD (реакции, отложенные сообщения и так далее)
4. Архитектурные диаграммы должны быть согласованы между собой, с PRD и OpenAPI-схемой

### Требования к описанию схемы базы данных

1. Все артефакты должны быть в каталоге `docs/` — например, в `docs/data/` или `docs/schema/`
2. Должна быть диаграмма логической схемы базы данных, построенной по правилам реляционной модели
    - выбраны таблицы и колонки — в терминах реляционной модели это отношения и атрибуты
    - выбраны ключи в каждой таблице — один первичный `PK`, ноль или более альтернативных `UK`
    - выбраны внешние ключи `FK` для представления связей
3. Диаграмма логической схемы данных реализуется с помощью языка разметки — Mermaid либо PlantUML
4. Должно быть описание физической схемы базы данных — например, в виде SQL с комментариями
    - под комментариями понимаются комментарии в SQL-коде (начинаются с `--`), а не метаданные схемы (`COMMENT`)
    - описание составляется для выбранной СУБД с учётом её особенностей — например, для Postgres 18
5. Логическая и физическая схемы должны быть согласованы друг с другом, с PRD, OpenAPI-схемой и диаграммами C4

### Общие требования архитектурной документации

Эти требования относятся к каждому артефакту данной лабораторной:

- Документ написан студентом или полностью вычитан студентом.
- Документ согласуется с другими документами в проекте.
- Документ легко читается человеком.
- Проверен LLM по аспектам:
    - полнота: нет «слепых пятен»;
    - нет противоречий внутри документа;
    - нет логических, фактических, грамматических и стилевых ошибок;
    - нет ошибок форматирования Markdown;
    - достижимость: проект можно реализовать за три месяца параллельно с другими курсами.

### Требования к ADR (необязательное задание)

>Это необязательное задание: вы можете не добавлять ADR.

ADR — это Architecture Decision Records, то есть документ, предназначенный для фиксации архитектурных решений.

1. Каждый ADR — это markdown-файл, описывающий одно архитектурное решение и его контекст (проблема, плюсы/минусы альтернативные решения)
2. Текст ADR должен быть минималистичным и лаконичным, несущественные детали можно опускать
3. ADR должен быть согласован с PRD и диаграммами C4

### Требования к слою доступа данных в бэкенде (необязательное задание)

>Это необязательное задание: вы можете не добавлять хранение данных на бэкенде.

Если вы добавляете слой доступа к данным в приложение, то:

1. Рекомендуется использовать СУБД Postgres для хранения данных
2. Рекомендуется запускать СУБД Postgres с помощью docker compose, а не устанавливать локально
3. В бэкенде слой доступа к данным может использовать как прямую работу с SQL-соединением, так и ORM
    - для C# и Postgres рекомендуется использовать `Npgsql`
    - использование ORM допускается, но не рекомендуется, поскольку ORM сложнее в понимании и отладке
4. Код бэкенда следует разделить на слои, например:
    - слой Presentation — содержит API handlers или API controllers
    - слой Application — содержит Service Layer (классы-сервисы) либо Use Cases
    - слой Data или Infrastructure — содержит классы / функции, инкапсулирующие доступ к СУБД
    - допускается иное деление на слои, если обеспечивается разделение ответственности не хуже, чем в примере выше
    - слои должны быть изолированы — например, это могут быть разные namespace в C# или разные пакеты в Go
