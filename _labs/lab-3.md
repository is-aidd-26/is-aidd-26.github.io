# Лабораторная 3: Разработка ядра сервиса

Для публикации в систему ASAP используйте ветку `03_core`

## Цели

**Основная цель:** разработать основное ядро сервиса — реализовать фронтенд и бэкенд, добавить хранение данных в реляционной СУБД.

**Дополнительная цель:** реализация дополнительной фичи, которая изначально не задумывалась.

## Задания

Обязательные:

1. Разработать рабочую версию бэкенд-части — основной функционал продукта (ключевые требования из PRD)
2. Разработать рабочую версию фронтенд-части — основной функционал продукта (ключевые требования из PRD)
3. Реализовать хранение данных продукта в реляционной СУБД

Необязательные:

1. Представить себя на месте пользователя: запросить новый функционал или доработку, которые изначально не задумывались, проработать требования и реализовать их в сервисе. Желательно, чтобы feature request затрагивал и бэкенд, и фронтенд
2. Реализовать логгирование действий пользователя в бэкенд-части
3. Упаковать фронтенд и бэкенд в docker-контейнеры (по желанию, можно вместо этого запускать их прямо на хосте)

## Требования

### Общие требования к коду

1. Код компилируется и запускается без ошибок и предупреждений
2. Реализованы ключевые требования к приложению из PRD
3. Реализация соответствует документации: спецификации, OpenAPI-схеме, архитектурным диаграммам и ER-диаграммам
4. В документации проработаны и полностью описаны дополнительные фичи

### Требования к хранению данных

1. Данные продукта хранятся в реляционной клиент-серверной СУБД
    - рекомендуется Postgres
    - тажке допускаются MySQL и другие клиент-серверные реляционные СУБД
    - не допускаются встраиваемые реляционные СУБД, то есть SQLite
    - не допускаются нереляционные СУБД (Redis, MongoDB и другие)
    - не допускается хранение в обычных файлах
    - не допускается хранение только в памяти процесса
2. Все ключевые данные продукта — чаты, сообщения и другие сущности — хранятся в СУБД и переживают перезапуск бэкенда
    - загруженные файлы, логи допускается хранить вне СУБД
3. Фактическая схема базы данных соответствует логической и физической схемам из документации
    - схемы в документации проектировались в предыдущей лабораторной
    - вы можете их обновить
4. Есть возможность развернуть проект с нуля с правильной схемой базы данных
    - рекомендуется реализовать механизм версионированных миграций с помощью готовых библиотек
    - допускается также использовать SQL-скрипт, выполняемый бэкендом автоматически, либо иначе генерировать схему при запуске бэкенда
6. СУБД запускается через docker compose как сервис в `docker-compose.yml` — даже если фронтенд и бэкенд запускаются на хосте без контейнеров

### Требования к тестированию

1. Студент проверил свой проект вручную, запустив его локально
2. Основные пользовательские сценарии воспроизводятся от начала до конца

### Требования к запуску через docker (необязательное задание)

>Это необязательное задание: вы можете не упаковывать фронтенд и бэкенд в docker-контейнеры, а запускать их прямо на хосте. СУБД при этом всё равно запускается через docker compose — см. требования к хранению данных.

1. Бэкенд и фронтенд упакованы в разные контейнеры и запускаются через общий `docker-compose.yml`
2. Docker-образы для фронтенда и бэкенда собираются через Dockerfile и секцию `build:` в `docker-compose.yml`
