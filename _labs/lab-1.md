## Цели

**Основная цель**: разработать спецификацию и спроектировать API бэкенда.

**Дополнительная цель**: добавить простейший фронтенд и бэкенд с одной функцией: отправка сообщения без сохранения.

## Задания

Обязательные:

1. Выбрать вариант проекта
2. Написать PRD (Product Research Document) в формате markdown
3. Спроектировать API и описать в формате OpenAPI v3
4. Добавить фронтенд на TypeScript / React с одной формой отправки сообщения

Необязательные:

- Добавить бэкенд на C# / AST.NET с одним методом API для отправки сообщения, без сохранения

## Требования

### Требования к спецификации

>Из этих требований можно составить хороший промпт — это ваша задача.

1. Написана либо полностью вычитана студентом
2. Описаны все функциональные требования
3. Легко читается человеком
4. Проверена LLM по следующим аспектам:
    - полнота спецификации: нет «слепых пятен», нет упущенной функциональности, необходимой для других возможностей продукта
    - нет противоречий внутри документа
    - нет логических, фактических, грамматических, стилевых ошибок в тексте
    - нет ошибок форматирования markdown
    - достижимость: проект может быть реализован студентом за три месяца параллельно с другими курсами

### Требования к описанию API

>Из этих требований можно составить хороший промпт — это ваша задача.

1. API описан в YAML-файле в формате OpenAPI v3
2. Нет противоречий между OpenAPI схемой и спецификацией
3. Вы должны выбрать, какому уровню зрелости REST API по Ричардсону следовать — 1-му или 2-му. Стиль должен быть единообразным в рамках выбранного уровня зрелости.
4. Вы должны учитывать дополнительные требования к OpenAPI, указанные ниже.

#### 1-й уровень зрелости REST API

В этом случае API рекомендаций меньше,:

1. HTTP Method выбирается по влиянию операции на данные
    - GET — идемпотентное чтение
    - POST — создание и обновление данных
    - DELETE — удаление данных
2. URL Path может содержать существительные и глаголы
    - пример: `POST /chats/1018/add-message` — добавление сообщения в чат с ID=1018
    - пример: `GET /chats` — получение списов чатов
    - пример: `GET /chats/1018` — получение сообщений чата с ID=1018
3. Слова разделяются дефисом (kebab-case)
    - Пример: `add-message`
4. HTTP-статусы соответствуют стандартам
    - Успешные коды: 200-299
    - Ошибки клиента: 400-499
    - Ошибки сервера: 500-599

#### 2-й уровень зрелости REST API (RESTful)

В этом случае API должен следовать рекомендациям RESTful:

1. HTTP Method обозначает действие
    - GET — идемпотентное чтение
    - POST — создание ресурса
    - PUT — обновление ресурса целиком
    - PATCH — обновление некоторых полей ресурса
    - DELETE — удаление
2. URL Path содержит существительные и описывает коллекции и сущности, коллекции — во множественном числе
    - пример: `GET /v1/users` — получение списка пользователей
    - пример: `GET /v1/user/10218/avatar` — получание аватара пользователя с ID=10218
3. Слова разделяются дефисом (kebab-case)
    - Пример: `POST /v1/learning-modules/10218`
4. HTTP-статусы соответствуют стандартам
    - Успешные коды: 200-299
    - Ошибки клиента: 400-499
    - Ошибки сервера: 500-599

### Требования к OpenAPI

1. Есть описание успешных ответов и ошибок
2. Единообразный формат ответа для ошибок
3. Все объекты описаны в “components:”
4. Строгая валидация полей для запросов
5. Реалистичные примеры в “example:”

### Требования к фронтенду

Требования к UI:

1. Есть только форма отправки сообщения в чат и список отправленных
2. Расположение формы отправки и списка отправленных — привычное для пользователя подобных приложений
3. «Недоделок» и лишнего в UI не должно быть

Требования к реализации:

1. В README.md описано как собрать и запустить фронтенд
2. Инструкция по сборке и запуску работает без очевидных проблем у преподавателя на Unix-системе (OSX / Linux)
3. Сборка выполняется без ошибок и предупреждений
4. Если нет бэкенда, то вместо него есть работоспособная заглушка
5. Если есть тесты, то они выполняются без ошибок и предупреждений
    - добавлять тесты в первых лабораторных не требуется

### Требования к бэкенду

>Это необязательная цель — вы можете не делать бэкенд в 1-й лабораторной.

1. Есть только метод отправки сообщения и он только пишет принятое сообщение в логе
    - «недоделок» в API не должно быть
    - базы данных не должно быть
2. В README.md описано как собрать и запустить бэкенд
3. Инструкция по сборке и запуску работает без очевидных проблем у преподавателя на Unix-системе (OSX / Linux)
4. Сборка выполняется без ошибок и предупреждений
5. Если есть тесты, то они выполняются без ошибок и предупреждений
    - добавлять тесты в первых лабораторных не требуется
